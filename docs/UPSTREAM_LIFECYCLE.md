# 上游依赖生命周期管理（UPSTREAM LIFECYCLE）

> 本仓库依赖多个外部仓库/服务。第三方依赖**必然演化或失效**，本文件用「增/活/衰/替」四阶段管理每个依赖，避免"接了就不管"。
> 框架借鉴 `lx-music-source` 的接口生命周期管理，实证前提：依赖会死（接口 -403 / IP 封禁 / 上游转向）。

## 一、依赖清单

| 依赖 | 关系 | 当前版本/引用 | 失效风险 |
|---|---|---|---|
| `lyswhut/lx-music-mobile`（上游原版） | fork 源头 | fork 点 `fb848072`（v1.9.1） | 中：上游持续开发，分叉后差异累积 |
| `luanmuc/lx-music-source`（音源） | CI 构建时拉取 | 每次构建取最新 master | 高：依赖第三方接口（K7） |
| `luanmuc/react-native-track-player`（fork） | 播放器依赖 | commit `0f0acb4`（b77 升级：自 `e1989e7` 重放定制补丁至上游 `8f56952` 基线） | 中：上游升级需重新应用定制补丁（K5） |
| npm 包 `luanmuc-lx-music-version-info` | 更新检查数据源 | CI 自动发布 | 低：NPM_TOKEN 失效时发布失败 |

## 二、四阶段框架

### 增（引入新依赖）
- **闸门**：新依赖必须有明确用途、最小引入面（能复用内置库就不新增）；
- **记录**：在本文档依赖清单 + `package.json` 中记录精确引用（commit/tag）；
- **默认关**：能力类依赖先默认关闭验证，实测可用再开启（与音源新增流程同思路）。

### 活（监控与升级时机）
- **上游 lyswhut**：关注上游 release/提交；出现与定制点相关的新功能或安全修复 → 评估合并（流程见 [MERGE_GUIDE.md](../MERGE_GUIDE.md)）；
- **track-player fork**：上游发版时，先 diff fork 定制补丁（通知栏按钮等），评估冲突面再决定是否跟进；
- **音源仓库**：App 每次构建自动拉取，无需手动升级；观察构建日志的音源版本行确认已更新；
- **npm 版本信息**：发布失败会在 Actions 出现 `::error::`，需更换 `NPM_TOKEN` secret。

### 衰（识别失效信号）
| 信号 | 含义 | 动作 |
|---|---|---|
| 上游长时间无维护 / 定制点被上游大改 | fork 漂移加剧 | 评估"继续分叉" vs "大合并"（决策点） |
| track-player fork 与新版 RN 不兼容 | 升级阻塞 | 评估换回上游版 + 放弃部分定制（通知栏按钮） |
| 音源接口大面积失效 | 依赖第三方 API 的系统性风险 | 按音源仓库生命周期管理处理（其 D 系列缺陷表） |
| npm 发布持续失败 | 更新通道受损 | 检查 token / 换通道（publish/version.json 兜底） |

### 替（替换路线）
- **上游**：无替换（fork 是本质）；"替"= 大合并或放弃跟踪，需用户决策；
- **track-player**：替换回官方版（接受定制项缺失）或 fork 自己维护（成本高）；
- **音源**：音源仓库已内置多子源冗余 + 降级链 + 健康自愈，单点失效不致命；
- **npm 版本信息**：App 端多源并行取最高版本（`utils/version.js`），jsdelivr/version.json 兜底。

## 三、观察与记录

- 每次合并上游 / 升级 fork，在提交说明记录：**依据**（上游 commit/版本）、**验证**（L0-L4 哪几层）、**结论**（合入/放弃/暂缓 + 原因）；
- 决策点（自建服务/大合并/放弃定制）必须由用户拍板，本文件只记录选项与成本；
- 更新本文档时同步更新 [KNOWN_ISSUES.md](./KNOWN_ISSUES.md) 对应条目状态。
